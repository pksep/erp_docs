Плановая дата готовности (`plan_ready_time`) и расчетное начало (`calculate_start_time`)
 

## Назначение

Эта логика отвечает на вопрос: "К какому сроку должна быть готова каждая операция, чтобы изделие, сборка или деталь успели к нужной дате?"

Для этого у операции есть два плановых поля:

| Поле | Что означает |
| --- | --- |
| `plan_ready_time` | Плановый срок завершения операции |
| `calculate_start_time` | Теоретическое время начала операции, рассчитанное назад от `plan_ready_time` |

Эти поля не являются фактическим расписанием сотрудника или станка. Они показывают плановую цепочку сроков внутри техпроцесса.

Фактическое расписание хранится отдельно в `start_time`.

## Главное правило расчета

Система считает сроки назад: от нужной даты готовности к первой операции.

Формула для одной операции:

```text
calculate_start_time = plan_ready_time - время выполнения операции
```

Время выполнения операции считается как:

```text
подготовительное время + (основное время + вспомогательное время) * количество в партии
```

Вычитание идет по производственному календарю, то есть система учитывает рабочее время, а не просто отнимает минуты по обычным часам.

## Как строится цепочка операций

Для каждого производственного контура система берет операции и сортирует их от последней к первой.

1. Последняя операция получает `plan_ready_time` из опорной даты.
2. Для нее считается `calculate_start_time`.
3. Предыдущая операция получает `plan_ready_time`, равный `calculate_start_time` следующей операции.
4. Так система идет назад до первой операции.

Пример:

| Операция | Плановый срок завершения | Расчетное начало |
| --- | --- | --- |
| Операция 3 | 20 мая 12:00 | 20 мая 09:00 |
| Операция 2 | 20 мая 09:00 | 19 мая 11:00 |
| Операция 1 | 19 мая 11:00 | 19 мая 08:00 |

Так видно, когда каждая операция должна закончиться, чтобы следующая успела начаться вовремя.

## Откуда берется опорная дата

Опорная дата — это дата, от которой начинает считаться вся плановая цепочка.

Система сравнивает доступные источники и берет более раннюю дату.

| Источник | Для каких сущностей | Что означает |
| --- | --- | --- |
| Родительская сборка или изделие | Детали и сборки | Когда родителю понадобится эта сущность |
| Складская потребность | Изделия, сборки, детали | Когда сущность должна быть готова на склад |

Для деталей родительская дата берется по фактическому старту первой операции родительской сборки.

Для сборок родительская дата берется по расчетному началу первой операции родительской сборки или изделия.

Для изделий родительской даты нет, поэтому опорой может быть только складская потребность.

Если ни один источник не дал дату, `plan_ready_time` и `calculate_start_time` становятся пустыми.

## Как выбирается складская дата

Складская дата берется не как просто минимальная дата среди заказов склада.

Система считает открытый спрос по активным позициям склада:

```text
открытый спрос = max(заказано к отгрузке - уже создано, 0)
```

Потом позиции сортируются так:

1. сначала позиции без даты;
2. затем позиции с датой по возрастанию;
3. при равенстве дат — по меньшему `id`.

Система накапливает открытый спрос и сравнивает его с текущим количеством сущности на складе.

Первая позиция, на которой накопленный спрос стал больше текущего количества, считается первой дефицитной.

Если у первой дефицитной позиции есть дата, она и становится складской опорной датой.

Если первая дефицитная позиция без даты, система берет ближайшую следующую позицию той же сущности с заполненной датой.

Если такой даты нет, складской источник возвращает пусто.

## Что происходит после расчета

Система сохраняет новые `plan_ready_time` и `calculate_start_time` у операций.

Сохранение выполняется так, чтобы не запустить повторный пересчет через те же хуки.

В текущем коде после `actualReadyPlanDateByEntity` не запускается автоматический пересчет очередей сотрудников или оборудования. Плановая дата и фактическое расписание остаются разделенными процессами.

## Каскад по дереву спецификации

Пересчет обрабатывается очередью `ActualTaskRelative`.

Если событие пришло для изделия, сборки или детали, процессор:

1. пересчитывает плановые даты этой сущности;
2. находит дочерние элементы первого уровня;
3. ставит их в такую же очередь пересчета.

Так каскад идет сверху вниз: родитель влияет на детей, дети — на своих детей.

## Когда запускается пересчет плановых дат

Пересчет запускается, когда меняется источник плановой даты или релевантность операции.

Основные случаи:

| Ситуация | Почему влияет |
| --- | --- |
| Изменилась дата готовности в позиции складского заказа | Может измениться складская опорная дата |
| Позиция складского заказа ушла в архив или вернулась | Может измениться набор активных складских источников |
| Изменилось заказанное или созданное количество в позиции склада | Может измениться первая дефицитная позиция |
| Изменилось количество изделия, сборки или детали на складе | Может измениться момент дефицита |
| Изменилась плановая дата операции | Может измениться релевантность связанных операций |
| Изменилась архивность операции или производственного контура | Может измениться набор участвующих операций |

## Что не является прямым триггером

Обычное изменение `start_time` больше не означает, что нужно пересчитать `plan_ready_time`.

`start_time` зависит от загрузки сотрудника или станка. Если использовать его как основу плановых сроков, каждое движение в расписании могло бы запускать лишний каскад по спецификации.

Поэтому плановая цепочка строится через `calculate_start_time`, а не через фактический `start_time`.

Исключение: для деталей родительская дата сейчас берется из `start_time` первой операции родительской сборки, потому что именно фактический старт сборки показывает, когда деталь действительно понадобится в производстве.

## Различие между планом и расписанием

| Вопрос | Поле |
| --- | --- |
| Когда операция должна быть готова по плану? | `plan_ready_time` |
| Когда теоретически надо начать, чтобы успеть? | `calculate_start_time` |
| Когда операция реально стоит в очереди ресурса? | `start_time` |

Если сотрудник перегружен, `start_time` может быть позже `calculate_start_time`. Это означает риск опоздания, а не ошибку расчета плановых сроков.

## Короткая памятка

| Ситуация | Что делает система |
| --- | --- |
| Есть складская потребность | Берет первую дефицитную дату по накопленному спросу |
| Есть родительская потребность | Сравнивает ее со складской датой и берет более раннюю |
| Нет ни одной даты | Оставляет плановые даты пустыми |
| Есть несколько операций | Считает сроки назад от последней к первой |
| Сдвинулась очередь ресурса | Плановые даты сами по себе не пересчитываются |
